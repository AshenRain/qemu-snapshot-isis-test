# Отчёт: выживаемость IS-IS и BFD при восстановлении QEMU из снапшота

Дата проведения: 20 августа 2026. Все времена в отчёте — UTC (локальное = UTC+2).

---

## Краткий вывод

**Тест B (главный) пройден.** После 15 минут с полностью остановленными процессами QEMU холодный старт с `-loadvm` занимает **3.4 с**, и соседство IS-IS оказывается в состоянии Up немедленно, LSDB побитово совпадает с эталоном, маршруты до loopback'ов соседа на месте. Ни ручного вмешательства, ни ожидания повторной сходимости не потребовалось.

**Тест C: BFD с таймерами 300 мс × 3 восстановление не переживает.** Сессия рвётся и утягивает за собой соседство IS-IS (`Adjacency flaps: 1` ровно в момент старта). Восстанавливается сама: BFD за ~3–4 с, маршруты полностью — за ~34 с.

**Главное обнаружение, не предусмотренное планом.** Значение имеет не длительность простоя между снимком и его использованием (она может быть любой — тест B это доказал), а **длительность самого `savevm`**. Пока QEMU пишет память на диск, vCPU стоят, но счётчик времени внутри гостя продолжает идти. При возобновлении все гостевые таймеры оказываются просроченными ровно на длительность записи. Именно это, а не механизм снапшотов, ломает BFD и — при аномально долгой записи — убивает FRR через systemd-watchdog.

### Сетевая обвязка

Выбран вариант **tap-интерфейсы на хостовом Linux-бридже**, а не `-netdev socket` — именно из-за предупреждения в плане.

```
br-isis (bridge, forward_delay 0, stp off)
  ├── tap1 → VM1 eth1 (10.0.0.1/30)
  └── tap2 → VM2 eth1 (10.0.0.2/30)
```

Второй интерфейс (`eth0`, user-mode NAT) использовался только для установки FRR из apt и проброса ssh; в тестах не участвовал.

**Результат по связности: проблем не было ни разу.** Бридж и tap-интерфейсы созданы на хосте персистентно и пережили полное завершение процессов QEMU: во время простоя интерфейсы переходили в `NO-CARRIER`, при старте VM несущая возвращалась автоматически. Порядок запуска VM не имел значения — обе поднимались параллельно. Ручного восстановления связности не требовалось никогда. Это подтверждает рекомендацию плана: для сценария с холодным рестартом tap+bridge предпочтительнее сокета.

### Конфигурация IS-IS

Как в плане, плюс loopback'и. VM1 (VM2 симметрично: `10.0.0.2/30`, `net 49.0001.0000.0000.0002.00`, `2.2.2.2/32`):

```
interface lo
 ip address 1.1.1.1/32
 ip router isis CORE
 isis passive
!
interface eth1
 ip address 10.0.0.1/30
 ip router isis CORE
 isis circuit-type level-2-only
 isis network point-to-point
!
router isis CORE
 net 49.0001.0000.0000.0001.00
 is-type level-2-only
 metric-style wide
```

Демон `bfdd` был включён в `/etc/frr/daemons` с самого начала, чтобы тест C не требовал перезапуска FRR (это сбросило бы соседство и смазало картину).

### Как снимались показания

Команды в гостях выполнялись через **последовательную консоль** (`ttyS0` с автологином root, выведенная в unix-сокет), а не через ssh. Причина принципиальная: ssh-сессия рвётся при восстановлении из снапшота, а сессия на serial-консоли живёт в памяти гостя и восстанавливается вместе с ней. Вся консоль параллельно писалась в файл, чтобы поймать возможные паники.

## 2. Размер снапшота

| Объект | Размер |
|---|---|
| Базовый Ubuntu cloud image (эталон для сравнения) | 596 МБ |
| Диск VM сразу после создания (qcow2 8 ГБ, FRR установлен) | 1.75 ГБ |
| **`VM_SIZE` одного снимка** | **917–950 МБ** |
| RAM гостя | 1024 МБ |

**Снапшот весит примерно как RAM гостя — почти один к одному.** Сжатия нет, экономия только на нулевых страницах, которые QEMU пропускает; у этого гостя их почти не осталось (571 МБ в page cache), отсюда 917 из 1024. Относительно образа: один снимок тяжелее базового cloud-образа в 1.5 раза и составляет около половины диска VM. Вклад дисковой части (COW изменённых кластеров) пренебрежим — между снимками гость почти не писал на диск, так что эти 917 МБ практически чистая память.

Механика роста файла (измерено на vm1.qcow2, объясняет заодно разброс времени записи из §3):

```
savevm при наличии свободных кластеров внутри файла:   +0 МБ,   1.16 с
savevm, когда файлу нужно физически вырасти:         +917 МБ,   1.78 с
delvm обоих снимков:  3298 МБ → 2381 МБ реально занятого
```

Логический размер qcow2 только растёт и никогда не сокращается (в этом прогоне дошёл до 4.2 ГБ), но реально занятое место после `delvm` возвращается ядру — qcow2 пробивает дыры в разреженном файле. Когда свободные кластеры внутри файла уже есть, следующий `savevm` не занимает дополнительного места и проходит быстрее.

**Главное следствие для планирования: размер снапшота определяется объёмом RAM узла, а не размером его диска.** Два узла по 1 ГБ дают ~1.8 ГБ на один сценарий. Реальный виртуальный роутер с 4–8 ГБ RAM даст 4–8 ГБ на узел, и при десятках сценариев именно память, а не диски, станет доминирующей статьёй расхода места. Если это упрётся в потолок — смотреть в сторону внешних снапшотов с общим backing-файлом, чтобы дисковая часть не дублировалась между сценариями.

## 3. Время `savevm` — и почему это самая важная цифра

| Прогон | VM1 | VM2 |
|---|---|---|
| Тест A | 4.008 с | 3.774 с |
| Тест B | **1.565 с** | **1.584 с** |
| Тест C | 2.054 с | 2.085 с |
| Серия повторов, итерация 1 | 2.049 с | **66.793 с** |
| Серия повторов, итерация 2 | 1.818 с | 1.783 с |
| Серия повторов, итерация 3 | 1.740 с | 1.710 с |
| Серия повторов, итерация 4 | 1.647 с | 1.632 с |
| Отдельный замер часов | 63.874 с | — |
| Прогон при засыпании хоста | 116.968 с | 118.207 с |

**В установившемся режиме — 1.6–2.1 с** на ~950 МБ, то есть около 500–600 МБ/с. Это соответствует ожиданиям от NVMe.

**Выбросы в 60–70 с воспроизводимы и объясняются ростом файла.** Когда qcow2 может переиспользовать освобождённые через `delvm` кластеры, запись быстрая. Когда файлу нужно физически вырасти, включается расширение разреженного WSL-VHDX поверх NTFS, и скорость падает до ~15 МБ/с. В серии повторов это видно прямо: первая итерация 66.8 с (файл рос), последующие — стабильно 1.6–1.8 с.

**Выброс в 117–118 с — артефакт засыпания хоста.** Windows ушла в Modern Standby в 11:48:07 UTC прямо посреди прогона (подтверждено событием Kernel-Power 506 в системном журнале). Этот прогон признан недействительным и переигран.

Для боевого применения вывод такой: держать qcow2 предварительно выросшим до рабочего размера (прогреть), либо уходить с VHDX на нативный Linux-хост.

## 4. Время `loadvm` — ключевая цифра

| Тест | Механизм | VM1 | VM2 | Обе параллельно (wall) |
|---|---|---|---|---|
| **A** | `loadvm` в живом процессе QEMU | 2.966 с | 3.184 с | **3.217 с** |
| **B** | холодный старт `qemu -loadvm` | 3.25 с | 3.38 с | **3.427 с** |
| **C** | холодный старт `qemu -loadvm` | 2.71 с | 2.79 с | **2.808 с** |

Для тестов B и C замерялось полное время запуска процесса QEMU, включая инициализацию машины и загрузку снапшота, — то есть именно то, что войдёт в бюджет эпизода RL.

**Разница между «разморозкой» и «холодным стартом» практически отсутствует: ~3 с в обоих случаях.** Это принципиально хорошая новость для архитектуры: не нужно держать пул замороженных QEMU-процессов, можно запускать процесс заново на каждый эпизод. Обе VM поднимаются параллельно, так что для топологии из N узлов время не суммируется.

Для сравнения: полная загрузка этих же VM с нуля до сходимости IS-IS занимала около 170 секунд (cloud-init + установка FRR + сходимость). **Выигрыш — примерно в 50 раз.**

## 5. Результаты по тестам

### Тест A — восстановление внутри одной сессии QEMU: ПРОЙДЕН

`savevm` → 15 минут работы VM → `loadvm`.

| Показатель | Эталон (до `savevm`) | Сразу после `loadvm` | Через 2 минуты |
|---|---|---|---|
| Соседство IS-IS | `vm2 eth1 L2 Up` | `vm2 eth1 L2 Up` | `vm2 eth1 L2 Up` |
| LSDB, `vm1.00-00` | seq `0x3`, chksum `0x1562` | seq `0x3`, chksum `0x1562` | seq `0x3`, chksum `0x1562` |
| LSDB, `vm2.00-00` | seq `0x3`, chksum `0x4a1c` | seq `0x3`, chksum `0x4a1c` | seq `0x3`, chksum `0x4a1c` |
| Маршрут `2.2.2.2/32` | есть, возраст 17:41 | есть, возраст 17:48 | есть, возраст 19:51 |

Соседство выжило, LSDB совпадает бит в бит, маршруты на месте. Симметрично на VM2 (`1.1.1.1/32` через `10.0.0.1`).

Показательная деталь: после `loadvm` номера последовательности LSP откатились с `0x4` на `0x3` — состояние вернулось к моменту снимка. Обе VM восстанавливались из снимков, снятых одновременно, поэтому рассинхронизации не возникло. **Это накладывает жёсткое требование на архитектуру: снимки всех узлов топологии должны сниматься и восстанавливаться согласованно.** Если восстановить один узел, а второй оставить работающим, соседний маршрутизатор увидит откат номеров последовательности LSP.

### Тест B — холодный рестарт: ПРОЙДЕН (главный критерий)

`savevm` → полное завершение процессов QEMU → 15 минут простоя → `qemu-system-x86_64 ... -loadvm snapB`.

Проверено: в момент простоя `pgrep qemu-system` возвращал 0, бридж и tap-интерфейсы оставались в системе в состоянии `NO-CARRIER`.

| Показатель | Эталон | Сразу после холодного старта | Через 2 минуты |
|---|---|---|---|
| Соседство IS-IS | `vm2 eth1 L2 Up`, holdtime 28 | `vm2 eth1 L2 Up`, holdtime 30 | `vm2 eth1 L2 Up`, holdtime 29 |
| LSDB, `vm1.00-00` | seq `0x5`, chksum `0x1164`, PduLen 93 | seq `0x5`, chksum `0x1164`, PduLen 93 | seq `0x6`, chksum `0x0f65`, PduLen 93 |
| LSDB, `vm2.00-00` | seq `0x5`, chksum `0x461e` | seq `0x5`, chksum `0x461e` | seq `0x6`, chksum `0x441f` |
| Маршрут `2.2.2.2/32` | есть, возраст 14:16 | есть, **возраст 14:20** | есть, возраст 16:23 |
| ping `10.0.0.2` | — | — | 3/3, 0% потерь |
| ping `2.2.2.2` | — | — | 2/2, 0% потерь |

**Возраст маршрута после восстановления (14:20) продолжает возраст до снимка (14:16)** — маршрут не переустанавливался, он просто продолжил существовать. Ни одного флапа соседства. Смена seq на `0x6` через 2 минуты — это штатное периодическое обновление LSP, не пересходимость.

Критерий успеха из плана выполнен полностью: соседство Up, LSDB совпадает с эталонной, маршруты до loopback'ов соседа на месте, без ручного вмешательства и без ожидания повторной сходимости.

### Тест C — BFD 300 мс × 3: НЕ ВЫЖИВАЕТ, но восстанавливается сам

Профиль BFD, привязанный к IS-IS через `isis bfd profile fast`:

```
bfd
 profile fast
  transmit-interval 300
  receive-interval 300
  detect-multiplier 3
```

Подтверждено на обеих сторонах: `Status: up`, интервалы 300/300 мс, multiplier 3 — то есть **detect time = 900 мс**. `savevm` при этом занял 2.05 / 2.09 с, то есть **вдвое дольше detect-таймера**.

Что произошло при холодном старте:

| Показатель | Значение |
|---|---|
| Сессия BFD, uptime до снимка | 4 мин 13 с |
| Сессия BFD, uptime после старта | **9 с** → сессия пересоздана |
| Флапы соседства IS-IS | **`Adjacency flaps: 1, Last: 4m12s ago`** — ровно момент старта |
| LSP после старта | PduLen **80** вместо 93 — из LSP исчез TLV соседа |
| Маршрут `2.2.2.2/32` сразу после старта | **отсутствует** |
| Маршрут через 2 минуты | есть, возраст 1:42 → переустановлен через **~34 с** после старта |
| Время восстановления BFD | **~3–4 с** |
| Полное восстановление маршрутов | **~34 с** |

Поллер с шагом ~80 мс, запущенный сразу после старта, все 60 сэмплов показывал `BFD=up` и `ISIS_ADJ=1`, но `ROUTE=0` — то есть к моменту первого сэмпла (через ~6 с) BFD уже успел переустановиться, а маршруты ещё нет. Факт разрыва доказывается сбросом счётчика uptime сессии и счётчиком флапов соседства.

FRR при этом **не перезапускался** (`ActiveEnterTimestamp` демона — за 6 минут до снимка, `NRestarts` не изменился). Это честная реакция протокола на просроченные таймеры, а не сбой демона.

**Сравнение с тестом B красноречиво:** без BFD — ноль флапов и маршрут с непрерывным возрастом; с BFD — флап соседства и 34 секунды до полного восстановления маршрутов.

## 6. Поведение времени в гостях

### Гость никогда не подхватывает время хоста

| Момент | Время в госте | Время на хосте | Отставание |
|---|---|---|---|
| После `loadvm` (тест A) | 11:26:54 | 11:42:25 | **−15 мин 31 с** |
| После холодного старта (тест B) | 11:47:21 | 12:35:53 | **−48 мин 32 с** |

Отставание монотонно накапливается и никогда не схлопывается. Связка `-rtc base=localtime,clock=vm` + отключённый NTP работает как задумано: при холодном старте QEMU восстанавливает часы из файла снапшота, и гость продолжает с момента снимка.

### Но часы гостя идут во время самой заморозки

Прямой замер: снимались `/proc/uptime` и `date` в госте до и после одного `savevm`.

```
savevm длился        63.87 с   (vCPU остановлены)
на хосте прошло      63.89 с
в госте прошло       64.97 с   ← ожидалось бы ~1 с
```

Пока QEMU пишет память на диск, гостевые vCPU стоят, но счётчик времени внутри гостя продолжает крутиться.

### Контрольный эксперимент: что именно попадает в просрочку

Чтобы разделить вклад записи, простоя и загрузки, проведён отдельный замер полного цикла: `savevm` → `quit` → простой → холодный старт. В госте снимался `/proc/uptime` до и после.

| Этап | Длительность на хосте |
|---|---|
| `savevm` (заморозка) | 63.05 с |
| простой с полностью убитым QEMU | 15.07 с |
| запуск QEMU с `-loadvm` | 1.96 с |
| накладные расходы замера | ~1.5 с |
| **всего на хосте** | **81.21 с** |
| **насчитал гость (`/proc/uptime`)** | **64.11 с** |

Гость насчитал ровно длительность `savevm` плюс накладные расходы. **Простой и загрузку он не заметил вообще.**

Причина в том, какое состояние часов попадает в файл снапшота. Последняя инструкция, которую гость успел выполнить, относится к *началу* записи; сохранённое состояние часов — к её *концу*. Разница между этими моментами и есть длительность `savevm`. Поэтому восстановленный гость — хоть через 15 минут, хоть через неделю — просыпается в убеждении, что с момента его последней инструкции прошло ровно столько, сколько длилась запись, и все его таймеры просрочены на эту величину.

**Длительность простоя между снимком и его использованием в этом неравенстве не участвует вообще.** Именно поэтому тест B прошёл чисто на 15 минутах, а тест C сломался на 2 секундах.

FRR фиксирует просрочку дословно:

```
Thread Starvation: {... timer r=-117.984  systemd_send_watchdog() ...} was scheduled to pop greater than 4s ago
Thread Starvation: {... timer r=-59.628 ...}
Thread Starvation: {... timer r=-6.690  wakeup_send_echo() ...}
```

Значение `r=` каждый раз равно длительности соответствующего `savevm` (118 с, 63.9 с, 7.25 с).

**Это и есть настоящая причина всех наблюдавшихся сбоев**, и она объясняет, почему в тесте A всё прошло гладко, а в тесте C — нет. Эффект присутствовал всегда, просто не везде переходил порог:

| Заморозка | Что задето | Последствие |
|---|---|---|
| 2.05 с (тест C) | detect time BFD = 900 мс | разрыв сессии BFD, флап соседства, 34 с до маршрутов |
| 1.6–4.0 с (тесты A, B) | ничего: holdtime IS-IS 30 с, watchdog 60 с | последствий нет |
| 118 с (при засыпании хоста) | `WatchdogSec=60` у `frr.service` | systemd убил FRR сигналом 6 |

**Оговорка:** замер сделан в WSL2 с вложенной виртуализацией, где kvmclock может вести себя не так, как на голом железе. Проверить на bare-metal стоит отдельно. На инженерный вывод «держи заморозку короче самого короткого таймера в стенде» это не влияет.

## 7. Ошибки, паники, зависания

**Паник, oops, hung task и зависаний консоли не зафиксировано ни разу** — консольные логи обеих VM за все восстановления проверены поиском по `kernel panic`, `Oops`, `BUG:`, `general protection`, `hung task`, `soft lockup`: ноль совпадений.

Единственный жёсткий сбой произошёл в прогоне, загрязнённом засыпанием хоста, и приведён здесь как предупреждение — с полным текстом:

## 8. Выводы для архитектуры RL-симулятора

**Механизм работает и даёт ожидаемый выигрыш.** Восстановление стенда из снапшота — ~3 секунды против ~170 секунд полной загрузки, то есть ускорение примерно в 50 раз. Простой между снятием и использованием снапшота роли не играет: 15 минут проверены, ограничений не видно.

**Что нужно учесть при проектировании:**

1. **Бюджет эпизода:** ~3 с на восстановление топологии из двух узлов. Узлы поднимаются параллельно, поэтому для бо́льших топологий время растёт слабо — упор пойдёт в дисковый ввод-вывод.

2. **Держать `savevm` коротким — это главное требование.** Длительность записи напрямую превращается в просрочку гостевых таймеров. Практический порог: заморозка должна быть заметно короче самого короткого detect-таймера в стенде. При 1.6–2 с это безопасно для IS-IS (holdtime 30 с) и заведомо небезопасно для BFD (900 мс).

3. **BFD с миллисекундными таймерами несовместим со снапшотами в лоб.** Если BFD нужен в сценарии — либо увеличивать интервалы так, чтобы detect time превышал длительность `savevm` с запасом, либо принять 34-секундную пересходимость в бюджете эпизода, либо поднимать BFD уже после восстановления.

4. **Снимать и восстанавливать все узлы топологии согласованно.** Иначе соседи увидят откат номеров последовательности LSP.

5. **Отключить systemd-watchdog у FRR в образе гостя** (`WatchdogSec=0`). Это дешёвая страховка от того, что единичный медленный `savevm` убьёт демоны и испортит эпизод незаметно для агента.

6. **Прогревать qcow2 до рабочего размера.** Пока файл растёт, `savevm` может занимать 60+ с вместо 1.7 с. Для продакшена — уходить с WSL-VHDX на нативный Linux-хост.

7. **Использовать tap на хостовом бридже, а не `-netdev socket`.** Проверено: обвязка переживает полное завершение QEMU, порядок запуска узлов не важен, ручное восстановление связности не требуется.

8. **NTP в гостях должен оставаться выключенным**, а гостевое время — считаться недостоверным. Отставание накапливается неограниченно (в этом прогоне дошло до 48 минут). Если сценарию нужны абсолютные временные метки, брать их с хоста, а не из гостя.
